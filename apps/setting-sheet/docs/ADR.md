# Architecture Decision Record (ADR)
プロジェクト: ライブハウス用セッティングシート作成アプリ

## 1. Vanilla JS（フレームワーク不使用）の採用
* **Context (背景):**
  本アプリは「ブラウザ上で完結するセッティングシート作成ツール」であり、将来的に他のメンバーが保守・改修する可能性や、サーバー環境（レンタルサーバー等）に単純にファイルを置くだけで動作する手軽さが求められていました。ReactやVueなどのモダンJSフレームワークを採用すると、Node.js環境やビルドパイプラインの構築が必須となり、保守のハードルが上がります。
* **Decision (決定):**
  ビルド不要で、どの環境でも `index.html` を開くだけで動作する **Vanilla JS（標準JavaScript）** を採用しました。モジュール分割（ES Modules）を活用し、`store.js`、`logic.js`、`ui.js`、`dragdrop.js`、`main.js` とレイヤーごとにファイルを分割することで、フレームワークなしでも十分な可読性と保守性を担保しています。

## 2. 状態管理（State Management）の `store.js` への集約
* **Context (背景):**
  機材の配置座標、回転角度、持ち込みフラグ、バンド情報など、アプリ内の状態（State）が複数のUIコンポーネント（ドラッグ処理、詳細モーダル、書き出し処理）から参照・変更されます。状態があちこちに分散すると、バグの原因になります。
* **Decision (決定):**
  ReactのReduxやVueのVuexのような状態管理パターンを参考に、**`store.js` を「単一の信頼できる情報源（Single Source of Truth）」として定義**しました。状態の変更は必ず `updateState` 関数を経由し、同時に自動で `localStorage` に保存される仕組みになっています。これにより、データ不整合を防ぎ、ブラウザの再読み込み時も安全に状態を復元できます。

## 3. ドラッグ＆ドロップの独自実装（ライブラリ不使用）
* **Context (背景):**
  SortableJSやInteract.jsなどのドラッグ＆ドロップライブラリの導入も検討しましたが、本アプリでは「スマホ操作時の指の腹で機材が隠れないように上にずらす（FAT_FINGER_OFFSET）」「回転モードと移動モードの切り替え」「ゴミ箱の当たり判定拡大」など、非常にニッチで細かいUX調整が必要でした。
* **Decision (決定):**
  外部ライブラリの制約に縛られることなく、完全なコントロールを得るために、標準の **Pointer Events API（`pointerdown`, `pointermove`, `pointerup`）を用いた独自実装** を採用しました。これにより、スマホとPCの両方で最適な操作感（タップとドラッグの判定分離など）を実現しています。

## 4. ステージ領域における `padding-top` ハックの採用
* **Context (背景):** 
  ステージ図面を「16:9」の比率でレスポンシブに描画する際、最新のCSS機能であるコンテナクエリ (`cqw`, `cqh`) や `aspect-ratio` を用いて高さを定義していました。しかし、Safari等の特定のブラウザ環境において「親要素の高さが暗黙的に計算される場合、子要素の絶対配置 (`position: absolute; height: xx%`) が正しく機能せず、要素が縦に伸びてしまう」という重大なレイアウト崩れバグが発生しました。
* **Decision (決定):**
  ブラウザ間の仕様解釈のブレを完全に排除するため、CSS 2.1時代から存在する枯れた技術である **「`padding-top` ハック」** を採用しました。親要素に `width: 100%; padding-top: 56.25%;`（16:9の場合）を指定し、擬似的に高さを確保。その内部に `position: absolute; top: 0; left: 0; width: 100%; height: 100%;` のコンテナを置くことで、どんな環境でも狂わない強固なレスポンシブコンテナを実現しています。

## 2. SVGアセットのレスポンシブ対応 (`preserveAspectRatio="none"`)
* **Context (背景):**
  ステージ上の機材アイコンは、ドラッグ＆ドロップで配置され、さらに「カスタム枠」等のようにサイズ比率が動的に変化する要件がありました。SVGデフォルトの仕様では、外枠の `div` や `img` の比率を変えても、内部のベクター画像は「元の縦横比」を維持しようとして余白ができてしまいます。
* **Decision (決定):**
  すべてのSVGファイルにおいて、ルートの `<svg>` タグに **`preserveAspectRatio="none"`** を付与する方針としました。これにより、外側のCSSで指定された幅・高さ (`width: 100%; height: 100%;`) に合わせてSVGが自在に変形するようになり、「自由枠」のサイズ変更などに柔軟に対応可能となっています。

## 3. DOM操作と画像書き出し (`html-to-image`) の共存
* **Context (背景):**
  ユーザーが「画像として保存」を実行した際、画面のUI上は別々の位置（ステージの下の操作エリアの中）にある「バンド情報」や「機材リスト」を、書き出し用の1枚の画像（PNG）内に含める必要がありました。
* **Decision (決定):**
  常に特定のDOM階層に固定すると、ユーザーが望む画面上の使いやすいレイアウト（パレットが図面の直下にある状態）が崩れてしまいます。そのため、**書き出しを実行する直前（同期処理中）に、JavaScript側で対象のDOMノード（バンド情報と機材リスト）を `export-container` 内へ一時的に移動し、書き出し完了後（`.finally`）に元の場所へ戻す** という動的DOM移動アプローチを採用しました。これにより、UXと機能要件を両立しています。

## 7. `main.js` 等の依存関係逆転（DIパターンの導入）
* **Context (背景):**
  初期実装では、`dragdrop.js`（ドラッグ処理）の中から直接 `ui.js` の関数やDOM変数をimportして操作しており、ファイル間の結合度が非常に高い（密結合）状態でした。これはテストがしづらくなる原因となります。
* **Decision (決定):**
  `setupDragDrop` 関数の引数（Config）として、操作対象のDOM要素やコールバック関数（`onChange`等）を外部から注入する **「依存性の注入（DI: Dependency Injection）」パターン** を採用しました。これにより、モジュール単体でのテストが容易になり、将来UIの仕様が変わってもドラッグ処理のロジックに影響を与えない堅牢な構造となっています。
