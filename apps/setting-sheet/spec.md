# ライブイベント セッティングシート作成システム 要件定義書 (spec.md)

## 1. プロジェクト概要・目的
* **目的**: ライブ出演者がスマートフォンから直感的にステージのセッティングシート（配置図）を作成・出力できるWebツール。PAや転換スタッフが当日のオペレーションをスムーズに行える正確な情報共有を目指す。
* **環境**: ロリポップサーバー上のWordPressページ内に、独立したHTML/CSS/JS（iframe等）として配置。
* **制約事項**: 
    * バックエンド（DBやサーバーサイド処理）は持たないスタンドアローン構成。
    * 状態管理はすべてフロントエンド（LocalStorage）で完結させる。

## 2. プロジェクト独自のドメイン知識（ユビキタス言語）辞書
AIが変数名や仕様を誤解しないための用語定義。
* **Stage**: 画面上部のステージ描画エリア。Phase 1ではシンプルな「真っ白な長方形キャンバス」とする。
* **Palette**: 画面下部の機材アイコン一覧エリア。
* **Equipment (機材)**: 配置可能なアイテム（Vocal Mic, Gt Amp, Ba Amp, Drum Set, Keyboard, DI, Chair, Music Stand, Table）。
* **Orientation (向き)**: アンプなどがステージ上のどの方向を向いているか（PAの音被り対策で重要）。
* **Ownership**: 備え付け機材（House）と持ち込み機材（Bring-in）の区別。

## 3. UI/UX・デザイントークンガイド
* **ターゲットデバイス**: Phase 1はスマートフォンでの動作（タッチ操作）をメインターゲットとする。
* **レイアウト構成**: スマホの「縦持ち」に最適化。画面を上下に分割し、上半分をStage（横長、アスペクト比 16:9 を基準とする）、下半分をPaletteおよび入力フォームとする。
* **操作性**: ドラッグ＆ドロップ（Touch Events対応）での配置。パレットに戻すことで削除。タップで向きの回転（45度刻み）。
* **視認性**: 持ち込み機材には視覚的なバッジ（例：「持」マークや枠線の色変更）を付与する。

## 4. Phase 1（MVP）のスコープ定義
* **実装する機能（In-Scope）**:
    * スマートフォン（主要モバイルブラウザ）での動作担保。
    * 基本情報（バンド名、日付、出演順）の入力。
    * 真っ白な長方形キャンバス（アスペクト比16:9）としてのステージ領域の描画。
    * スマホでの機材アイコンのドラッグ＆ドロップ配置。
    * アイコンのタップによる向き変更（回転）。
    * 備え付け / 持ち込みのトグル切り替え。
    * 誤操作防止のためのLocalStorageへの自動保存。
    * 4種類の機材配置プリセット機能（「スタジオOWL基本バンドセット」等）および特定のプリセットに応じた注釈（天井モニター等）や柱の表示。
    * 配置状態の「全クリア・リセット」機能（完全にクリアするか、スタジオOWLの初期状態に戻すかを選択可能なモーダル）。
    * **完成図の画像（PNG形式のみ）書き出し・ダウンロード（`html2canvas`等のフロントエンドライブラリを利用し、端末の解像度（devicePixelRatio）を考慮したscale指定により高画質で出力する）。**
* **やらないこと（Out-of-Scope / Phase 2以降の将来構想）**:
    * タブレットやPCでの大画面レイアウト最適化およびマウス操作（Click/Drag）対応。
    * 機材名のラベル編集（「Marshall」「JC-120」「持込Amp」など）。
    * 演奏者名の表示（Vo、Gt、Baなど）。
    * マイクスタンドの種類（ブーム／ストレート）の指定。
    * 「ここに譜面台」などの簡単なフリーテキストメモ機能。
    * Undo/Redo機能（スマホUIの都合上、Redoは除外しUndoのみ実装する可能性あり）。
    * 実際のステージ形状（スタジオOWLの平面図など）を反映した背景図の適用。
    * 詳細なテキスト情報の追加（マイク持ち込み詳細など）。
    * 回線表（チャンネルリスト）の自動生成。
    * ステージの形状・サイズのカスタマイズ機能。
    * ドラムセットの詳細設定（タム数、シンバル枚数など）。
    * システムからの直接メール送信機能。
    * 機材アイコン同士の衝突判定（重なって配置されても許容する）。
    * 複数人での同時編集機能（リアルタイム同期）。
    * 複数プロジェクト（複数のセッティングシート）の保存・管理機能。
    * ユーザーアカウント登録およびログイン機能。
    * PDF形式でのエクスポート機能。

## 5. UI層とLogic層の分離方針（必須要件）
* **Data & Logic層 (純粋関数)**:
    * 状態（State）の管理：ステージ上のアイテムの座標（Stageに対する%ベース）、種類、向き、持ち込みフラグ、z-index（重なり順）、基本情報テキスト。
    * ビジネスロジック：
        * ドラッグ終了時の座標判定（ステージ内かパレットか）。
        * 回転角度の計算（45度ずつ加算）。
        * pxから%への座標変換計算。
        * タップとドラッグの判定計算（`touchstart`から`touchend`までの移動距離を計算）。
        * 重なり判定：指定座標にあるアイテム群から `zIndex` が最大（最前面）のものを特定する処理。
        * z-index更新：操作対象となったアイテムの `zIndex` を最大値に更新し、最前面へ移動させる処理。
        * LocalStorageへのシリアライズ/デシリアライズ（エラー時の安全なフォールバック処理を含む）。
* **UI層 (DOM操作ベース)**:
    * Canvas APIを用いた自前での描画・当たり判定は行わず、UIはDOM要素（`div`や`img`）で構築する。
    * **機材アイコンは拡大縮小・回転に強く、画像化しても劣化しないSVG形式を使用する。**
    * Logic層からStateを受け取り、画面上にアイコンを`zIndex`順にDOMとして描画（CSSによる配置・回転）する処理のみを担当。
    * Touchイベントを検知し、デフォルトのスクロール挙動を確実に防止（`e.preventDefault()`）しつつ、Logic層に座標データを渡す。

## 6. Logic層のテストケース（入力と期待される出力）
TDDを前提とし、以下のコアロジックから実装・テストを行う。
1.  **配置・削除判定**: `checkDropLocation(x, y)` -> 座標がStage内なら `true`、Palette領域なら `false`（削除扱い）を返す。
2.  **回転ロジック**: `calculateNextRotation(currentDegree)` -> 現在の角度を受け取り、45度加算した値（360なら0）を返す。
3.  **アクション判定（タップ vs ドラッグ）**: `determineTouchAction(startX, startY, endX, endY, threshold)` -> 移動距離が閾値（例：10px）未満なら `'tap'`、閾値以上なら `'drag'` を返す。
4.  **最前面アイテムの特定**: `getTopmostItemAtPosition(x, y, items)` -> 該当座標に複数のアイテムが重なっている場合、`zIndex` が最も大きいアイテムのIDを返す。
5.  **自動保存とエラーリカバリ**: `saveToLocal(state)` / `loadFromLocal()` -> Stateオブジェクトを正しくJSON化して保存・復元できるか。また、JSONが破損していたり不正な形式だった場合はクラッシュせず、初期状態の空データを返すか。

## 7. 画面構成ごとの詳細要件とエッジケース
* **エッジケース1（画面外へのドロップ）**: Stage領域でもPalette領域でもない曖昧な場所にドロップされた場合は、元の位置に戻す（スナップバック）フェイルセーフを実装する。
* **エッジケース2（誤リロード）**: 初期読み込み時に `loadFromLocal()` を実行し、データが存在すれば「前回の続きから再開しますか？」の確認ダイアログ（またはシームレスな復元）を行う。
* **エッジケース3（スワイプ時の画面スクロール防止）**: スマホでのドラッグ操作中（`touchmove`）にブラウザ自体がスクロールしてしまわないよう、JS側でドラッグ領域におけるデフォルトのスクロール・スワイプアクションを無効化する。**さらにCSSで `touch-action: none;` を適用し、iOS（Safari）等の強力なネイティブスクロール（戻る/進む/バウンス等）も完全に封じる。**
* **エッジケース4（重なり時の操作）**: 重なっている機材をタップ・ドラッグした際は、必ず最前面（Topmost）の機材が操作対象となり、かつ操作された機材はさらに最前面へ再配置されること。
* **エッジケース5（保存データの破損・非互換）**: LocalStorageのパース時（`JSON.parse`）にエラーが発生した場合、または将来のアップデートでデータ構造の互換性が失われていた場合は、画面をクラッシュさせず、安全に「真っ白な初期状態」へフォールバックする。
* **破壊的変更**: 「すべてクリア（初期化）」ボタンを押す際は、必ず確認ダイアログ（`window.confirm`等）を挟む。

## 8. 決定事項まとめ（迷った時の議事録）
| 検討項目 | 決定事項 | 理由 |
| :--- | :--- | :--- |
| **ターゲットデバイス** | Phase 1はスマホに特化 | MVPとしての開発スコープを絞り、CSSやイベント処理の複雑化を防ぐため |
| **スマホ画面の向き** | 縦持ちのまま上下分割 | スクロールとドラッグ操作を両立させ、ユーザーの持ち替えストレスを無くすため |
| **ステージの比率** | アスペクト比 16:9 を基本とする | AIコーディング時のレイアウトのブレ（極端な縦長・横長化）を防ぎ、UIを安定させるため |
| **アイテムの削除** | パレットへドラッグして戻す | 画面が狭いスマホにおいて、小さな「×」ボタンをタップさせる誤操作を防ぐため |
| **データ出力方法** | PNG（高解像度書き出し） | サーバー側の保守コストを下げつつ、PAが拡大確認した際の視認性を確保するため |
| **アイコンの形式** | SVG形式を採用 | 拡大縮小・回転やPNG出力時の画質劣化を防ぐため |
| **ドラッグ時の挙動** | JS + CSS(`touch-action: none`) | iOS特有の強力なネイティブスクロールを貫通させず、致命的なUX低下を防ぐため |
| **初期ステージ形状** | 真っ白な長方形キャンバス | MVP構築において、描画ロジックの複雑化を防ぎ、最速で実装を完了させるため |
| **座標系の定義** | Stageに対する%（パーセンテージ）ベース | 端末の画面サイズ依存（px）によるレイアウト崩れを防ぎ、PNG書き出しの精度を担保するため |
| **タップ/ドラッグ判定** | 移動距離（px）での閾値判定を導入 | 「動かすつもりが回転した」などのスマホ特有の誤操作を防ぐため |
| **アイテムの重なり** | z-indexによる最前面管理 | 重なった機材の中で「意図しない奥の機材」を操作してしまう事故を防ぐため |
| **データ破損対策** | パース失敗時は初期状態へフォールバック | 予期せぬデータ不整合によるシステムの完全なフリーズ（ホワイトアウト）を未然に防ぐため |
| **描画・エクスポート方式** | UIはDOM構築、エクスポートはライブラリ使用 | Canvas APIでの当たり判定等の手動計算を避け、DOMの標準機能で実装コストを下げるため |

## 9. データスキーマ定義（Schema-Driven）
TypeScript (またはJSDoc) により、以下の型定義を最初に厳格に行う。

```typescript
type EquipmentType = 'vocal_mic' | 'gt_amp' | 'ba_amp' | 'drum_set' | 'keyboard' | 'di' | 'chair' | 'music_stand' | 'table';

interface PlacedItem {
  id: string;             // 一意のUUID
  type: EquipmentType;    // 機材の種類
  x: number;              // ステージ上のX座標（0〜100の相対%）
  y: number;              // ステージ上のY座標（0〜100の相対%）
  rotation: number;       // 角度 (0, 45, 90, 135, 180, 225, 270, 315)
  isBringIn: boolean;     // 持ち込みフラグ (true: 持ち込み, false: 備え付け)
  zIndex: number;         // 重なり順（タップ・ドラッグ時に最大値へ更新し最前面に配置）
}

interface StageState {
  eventName: string;      // イベント名
  bandName: string;       // バンド名
  playOrder: string;      // 出演順
  presetNote: string;     // プリセット固有の注釈テキスト（例：モニター天井吊るし）
  hasPillars: boolean;    // 会場（OWL）特有の柱表示フラグ
  items: PlacedItem[];    // 配置された機材の配列
}
```

## 10. 段階的導入の検討
* **採用**: データスキーマ駆動（型定義）、ADR（決定事項まとめとして`spec.md`に内包）。
* **見送り**: サーバーサイド処理を持たず、段階的な機能拡張はPhase 2に切り出しているため、CI/CDの完全自動化やフィーチャートグル、複雑なCDDはPhase 1ではオーバーエンジニアリングとみなし導入しない。
